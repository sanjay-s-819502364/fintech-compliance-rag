# Fintech Compliance RAG (AWS Bedrock)

A multi-jurisdictional regulatory RAG system over UK FCA and Australian ASIC
payments/e-money guidance — built on AWS Bedrock, with a documented
cross-jurisdiction retrieval failure and the fix for it.

## What this found

Naive RAG over a two-jurisdiction regulatory corpus returned Australian
guidance for a question that explicitly named the UK regulator — and the
specific guide it returned governed a different obligation entirely. The
embeddings were matching topic vocabulary ("complaints," "timeframes"), not
jurisdiction or obligation, because regulatory text describes the same
subjects in near-identical language across regimes.

Semantic search alone can't separate them. The fix: tag jurisdiction as
metadata at ingestion and filter *before* retrieval, rather than relying on
the embedding to carry it. In compliance, a confidently wrong
cross-jurisdiction answer isn't a bad answer — it's a regulatory breach. So
the system also enforces grounding and refuses rather than guesses when it
can't support an answer.

Full write-up, including the specific baseline measurements that surfaced
this: [`docs/baseline-findings.md`](docs/baseline-findings.md)

## Architecture

| Component | Choice | Notes |
|---|---|---|
| Corpus | 19 PDFs, ~1,000+ pages | UK FCA + AU ASIC — see [`SOURCES.md`](SOURCES.md) |
| Storage | S3, jurisdiction-prefixed | `corpus/uk-fca/`, `corpus/au-asic/` |
| Parser | Bedrock Data Automation | Extracts text + describes images/tables |
| Embeddings | Titan Text Embeddings V2 | 1024 dimensions |
| Vector store | Aurora PostgreSQL Serverless v2 + pgvector | HNSW + GIN indexes |
| Generation | Nova Lite / Nova Micro | |

## Eval harness

A 30-question eval set spans single-document lookups, jurisdiction-specific
questions, cross-jurisdiction "bait" questions (designed to trigger the
contamination bug), and unanswerable questions. Each question carries an
`answer_note` for claim-level scoring, not just document-level — a
document-level pass can still contain a wrong number if scored too coarsely.

- [`eval/eval-questions.json`](eval/eval-questions.json) — the question set
- `eval/results/` — generated answers + retrieved sources (gitignored — contains
  live `kb_id`/`guardrail_id`; regenerate with `python src/run_generation.py`)
- [`src/triage_eval.py`](src/triage_eval.py) — scoring logic

## Setup

```bash
pip install -r requirements.txt
cp .env.example .env   # fill in your AWS region + Bedrock IDs
```

This project does not include the source regulatory PDFs — see
[`SOURCES.md`](SOURCES.md) for links to the FCA's and ASIC's own hosted
copies, and the reasoning on why they're linked rather than committed.
Download them into a local `corpus/` folder (gitignored) before running
ingestion.

```bash
python src/generate_metadata.py    # tag jurisdiction/regulator/doc_type per file
python src/run_generation.py       # run the eval set against the deployed agent
python src/triage_eval.py          # score results
```

## Known limitations / next steps

- **Weak retrieval scores** (0.53–0.54) on well-covered topics — possibly a
  chunking artifact at the current 300-token size; worth re-testing at
  1000-token and hierarchical chunking.
- **Image-derived chunks outrank substantive prose** in some cases — needs
  investigation into whether to down-weight or exclude them.
- **Eval set provenance**: some questions were generated by inference from
  filenames/chapter titles rather than by reading every source PDF in full —
  a disclosed limitation, not a hidden one.
